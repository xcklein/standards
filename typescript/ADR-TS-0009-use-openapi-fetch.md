# Use openapi-fetch

## Directive

All typed HTTP requests to internal APIs must use `openapi-fetch` initialised with the generated `paths` type. Direct use of `fetch` or `axios` for typed API calls is not permitted.

## Context and Work Statement

Making HTTP requests to a typed API requires a client that enforces the correct request shape and narrows the response type based on the endpoint called. A generic `fetch` wrapper provides no type safety — wrong parameters and incorrect response handling are only caught at runtime. `openapi-fetch` uses the types generated by `openapi-typescript` to make every API call fully type-checked at compile time.

## Decision Drivers

* API calls must be type-safe — incorrect parameters or response handling must be compile errors
* The client must be lightweight with no runtime schema validation overhead
* The client must work in browser and server environments without configuration

## Considered Options

* openapi-fetch
* Plain `fetch` with manual typing
* axios

## Decision Outcome

Chosen option: "openapi-fetch", because it provides full compile-time type safety for every API call using the types generated by `openapi-typescript`, with zero runtime overhead and no schema validation.

### Examples

Create a typed API client:

```typescript
import createClient from "openapi-fetch";
import type { paths } from "./api.ts";

export function createApiClient(getToken?: () => Promise<string>) {
  const client = createClient<paths>({ baseUrl: import.meta.env.VITE_API_URL });

  if (getToken) {
    client.use({
      async onRequest({ request }) {
        const token = await getToken();
        request.headers.set("Authorization", `Bearer ${token}`);
        return request;
      },
    });
  }

  return client;
}
```

Make a type-safe API call — path, query parameters, and response are all typed:

```typescript
const { data, error } = await client.GET("/v1/users/{userId}", {
  params: {
    path: { userId: "01HXYZ" },
  },
});

if (error) {
  // error is typed as the API's error response schema
}

// data is typed as the 200 response schema
console.log(data.username);
```

### Consequences

* Good, because path, query, body, and response types are all inferred from the OpenAPI schema — no manual typing required
* Good, because zero runtime overhead — all type checking happens at compile time
* Good, because middleware support allows adding auth headers, logging, and retries cleanly
* Bad, because requires `openapi-typescript` to have been run — stale generated types give false confidence
* Bad, because the API surface changes require regenerating types before the client reflects them

### Confirmation

All HTTP requests to internal APIs must use an `openapi-fetch` client initialised with the generated `paths` type. Direct use of `fetch` or `axios` for typed API calls is not permitted.

## Pros and Cons of the Options

### openapi-fetch

* Good, because full compile-time type safety with zero runtime overhead
* Good, because middleware API for auth, retries, and logging
* Good, because tiny bundle size
* Bad, because tightly coupled to `openapi-typescript` generated types

### Plain `fetch` with manual typing

* Good, because no additional dependencies
* Bad, because types must be written and maintained manually
* Bad, because no enforcement that request shape matches the API contract

### axios

* Good, because widely adopted with a familiar API
* Good, because interceptors for auth and error handling
* Bad, because no OpenAPI integration — types must be maintained manually
* Bad, because larger bundle size than `openapi-fetch`
